# Project guidance

- Write code, UI text, and repository documentation in English.
- Prefer self-explanatory names, intention-revealing variables, and small helper functions to explain control flow. Avoid explanatory comments, empty catch blocks, and nested ternary operators; handle branching with early returns, guard clauses, or dedicated helper functions, and handle errors explicitly or safely transform them without discarding details silently. For HTTP contracts, infer OpenAPI schemas from explicit TypeScript request/response models as described in docs/architecture.md. Do not add descriptive JSDoc, @Example decorators, or @example tags solely to enrich Swagger; use its schema-derived sample values. Keep detailed examples and business semantics in docs/api-contracts.md. Retain concise error-response declarations and routing/authentication/status decorators.
- Keep the implementation small and focused on the challenge's mandatory requirements. The user approved only the optional performance exercise on a separate branch; follow `docs/performance-plan.md`. Do not add realtime or waitlist bonuses.
- Before making assumptions, consult `docs/challenge.md`, the local structured restatement of the challenge. Follow its mandatory requirements and distinguish them from project decisions. Do not invent requirements.
- Whenever the user comments on requirements or scope, re-read the relevant section of `docs/challenge.md` before answering or changing the plan. Explain whether the statement matches the brief, is mistaken, or adds scope, citing the relevant section. Do not silently accept a mistaken interpretation; an explicit user-approved scope change remains distinguishable from a challenge requirement.
- Start from `docs/execution-plan.md` and read its referenced API/UI/architecture/task/ADR specifications. `docs/decisions.md` is the consolidated approved register; implementation checkpoints are not additional product requirements. Do not rely on superseded chat proposals or discarded wireframe variants.
- For frontend work, read DESIGN.md, docs/design-system.md and docs/frontend-plan.md before implementation. Use the approved Aguinha-derived mockups indexed by docs/mockups/aguinha/REVIEW.md, existing web Tailwind and native HTML; Mantine/NativeWind/gluestack proposals are superseded. Danger buttons use white backgrounds with red text and red borders, never solid red fills. Keep the DS and handoff self-contained in this repository, including local mockups/fonts/photo credits; do not require the original Aguinha checkout or prior chats.
- Follow the approved feature-oriented architecture in `docs/decisions.md`: backend controllers, services, feature-specific repositories over Prisma, and presenters; frontend integration pages/hooks separate from presentational views receiving props and callbacks. Keep HTTP, authentication storage, and routing out of presentation. Presentational views must render in Storybook with props/fixtures and without API, auth, or router context; keep route/page containers outside Storybook unless a story explicitly supplies a small test harness. Add each application route with the screen/integration that needs it instead of prebuilding routes for future screens. Use a small set of Storybook page/component stories with fixtures; avoid generic CRUD repositories and unnecessary layers.
- For each implemented backend feature/domain repository, keep its interface in `<feature>Repository.ts` and its Prisma implementation in `prisma<Feature>Repository.ts` as `Prisma<Feature>Repository implements <Feature>Repository`. Services consume the interface; do not declare persistence contracts as Store interfaces inside services or framework adapters. Reuse the contract (or a narrow Pick) in authentication adapters. Keep the existing feature folders. Assemble concrete repositories, services and the authentication adapter manually in backend/src/dependencies.ts; services require repository interfaces in constructors and must not import or instantiate Prisma implementations. Controllers use composed services, and the tsoa authentication hook delegates to the composed adapter. Keep dependency imports acyclic. Do not add a DI container, generic repositories, or mandatory in-memory implementation. Apply to existing auth/courts and future implemented persistence features; do not create unused repositories for every Prisma model. See docs/architecture.md.
- Verify architecture explicitly before PR handoff and review approval. In backend feature code, controllers, services, and framework adapters (including authentication) access persistence through feature repositories; the database connection module, migrations/seed, and database integration setup are infrastructure exceptions. Services must not depend on Express/tsoa adapters. Inspect imports and direct database calls, follow an affected request flow, and record file/symbol evidence. Classify an objective boundary violation as a required project-convention fix even if behavior passes; do not call the delivery ready with this check missing. Avoid source-text tests and extra abstraction frameworks merely to enforce the rule.
- Resolve pending dependency versions autonomously using the latest stable release compatible with the approved stack whenever possible. Verify official requirements and peer dependencies, pin exact versions and a lockfile during setup, and exclude alpha/beta/RC builds. Do not ask the user to approve each routine version; discuss material incompatibilities that require changing approved decisions. Preserve already-approved pins unless a change is separately justified.
- Use PostgreSQL with Prisma. Earlier MongoDB/Mongoose and occupied-slot-array proposals are superseded. Keep snake_case within database artifacts and use camelCase throughout TypeScript and API JSON through Prisma's mapping configuration. Preserve database-level overlap protection in versioned migrations. The temporary D3.3a learning stage and D3.3b restoration are reviewed and merged; retain bookings_no_confirmed_overlap and the mapping of its actual database violation to BOOKING_CONFLICT/409. Keep the application precheck as advisory. For the observed booking INSERT deadlock only, the user approved exactly one retry after Prisma P2034 with driver SQLSTATE 40P01 confirms rollback. Keep the retry at the repository boundary, maximum two insert attempts; only the named exclusion violation becomes BOOKING_CONFLICT/409. Propagate exhausted/unrelated errors and never retry ambiguous network/commit failures or add client mutation retries. Preserve historical migrations and never silently delete/cancel application data to reinstall the constraint. Agent verification must use isolated courtly_test; do not apply migrations to the main application database.
- Seed the facility with IANA timezone `America/Sao_Paulo`. Use a generic monetary unit displayed with `$` and two decimal places, without labeling it BRL, USD, or another real currency. Interpret calendar dates and opening hours in the facility timezone and booking instants in UTC.
- Keep Facility as an internal seeded configuration entity; do not add facility listing, detail, or CRUD endpoints or facility selection screens. Use the Facility timezone for availability calculations; do not repeat it in court fields. Court `display` contains only the formatted hourly price. The mandatory administrator day view includes all courts and total expected revenue; no export or separate reporting subsystem is required.
- Follow `docs/api-contracts.md` for approved presentation contracts. Prepare English date, time, status, and generic-dollar labels in backend `display` objects. Expose structured values only when the client needs them for behavior or requests. Booking presentation responses omit raw start/end instants and numeric prices, retain IDs and machine-readable status, and include server-computed `canCancel`. Keep formatting out of persistence models; no separate BFF service is needed. Always revalidate permissions and cancellation timing when the action is submitted.
- `display` contains derived, formatted, or translated presentation strings only. Keep identifiers, action inputs, machine-readable states, booleans, and resource structure outside it. Original text such as court/user names also stays outside it. Include both a raw value and its label only when both have concrete client uses; omit unused fields. Put shared display context at the nearest common response level rather than repeating it in every item. Never parse display strings to recover structured values.
- Never return time intervals as combined strings or `display.timeRange`. For court opening hours, reuse existing `opensAt` and `closesAt` rather than duplicating them in `display`. Slots, personal booking responses (creation, listing, cancellation), and daily-report items use separate local `display.startsAt` and `display.endsAt` values. The client renders a spaced visual separator and an equivalent accessible `until` separator. Hide the visual separator from assistive technology and keep the accessible separator visually hidden; do not announce both. Accessibility and semantic markup are frontend responsibilities. This permits presentation composition without parsing combined labels or converting timezones and does not require adding raw booking timestamps.
- Apply the shared error contract and HTTP mappings in `docs/api-contracts.md`: `{ code, message }` with optional field-specific `fields`. Normalize errors consistently, document them in Swagger, and keep technical details in backend logs. Protected-operation 401 opens the authentication-error page with a login option; invalid login credentials stay on the login form. Keep form errors and conflicts on the current screen.
- Returning from review retains court/date/week, reloads availability, and clears all slot selections. Automatic restoration/stale-selection recovery is a future improvement. Daily report date is optional and defaults server-side to the current Facility-local day; the response date initializes the UI.
- Availability is weekly: Sunday through Saturday, current facility-local week when `weekStart` is omitted, and explicit Sunday validation when supplied. Return seven days with `isSelectable`, slots, and backend-generated previous/next API links as specified in `docs/api-contracts.md`. This replaces the older required daily `date` query. The client follows navigation links, shows booked slots disabled, hides past slots, and does not scan for a day with free slots.
- Focus on the happy path. Discuss additional edge-case behavior before implementing it.
- Keep backend Vitest unit/integration tests focused and simple. Cover real-PostgreSQL concurrent prevention, cancellation timing including exact equality, and opening hours. Use isolated courtly_test with application migrations. No automated frontend suite: demonstrate isolated presentation states in Storybook and manually verify main flows and native accessibility.
- Use the GitHub CLI (`gh`) for creating, inspecting and updating pull requests. Do not use the browser interface as a fallback for PR operations. If a tool context reports an authentication failure, check the available CLI execution context or report the concrete blocker; never silently switch to browser automation.
- Never commit directly to `main`. Use a feature branch and a pull request for review and merge.
- Branch names must describe only the feature or work being delivered, in lowercase kebab-case, without AI or agent references or prefixes. Examples: `planning`, `booking-creation`, `court-management`.
- Follow the Google-style commit format without a parenthesized scope: `<type>: <imperative English summary>`. Examples: `feat: add booking creation`, `fix: enforce cancellation window`, `docs: record project decisions`. Use `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, or `revert` as appropriate.
- Commit messages and PR titles and bodies must not include AI attribution, agent signatures, generated-by notices, or agent co-author trailers. This does not remove the challenge's separate requirement to disclose AI usage in the submission decisions.
- Commit planning documentation only when an entire coherent topic block is resolved and the user closes it, not after each field-level decision. During discussion, accumulate documentation changes without committing, keeping unresolved proposals clearly marked. For example, a daily-report response is one block: agree all its fields and behaviors before making one commit. Do not rewrite earlier commits to enforce this convention retroactively unless requested. When reporting a documentation commit, show its short hash, full subject, and the closed block's approved decisions. Historical documentation commits were explicitly authorized to use recorded original change times; do not invent timestamps or backdate future work without authorization.
- Documentation commit subjects must summarize the concrete decision or behavior approved, for example `docs: approve daily booking report response` or `docs: require dates for court availability`. Avoid generic subjects that merely announce recording decisions or updating documentation. The user-facing commit report must also briefly state which decisions were closed, alongside the hash and full subject.
- The user approved a one-time bootstrap exception: local `main` points to the existing initial commit `c8ce1f8` (initial AGENTS.md and planning decisions). All subsequent planning commits remain on `planning` for a PR into `main`. Preserve this history; the exception does not authorize future direct commits to `main` or agent merges. Publish the base and planning branch when preparing the first PR.
- Keep these instructions and the planning documents current as decisions change.
- Before implementation handoff or review completion, check all applicable project rules, not only the latest reported issue. Use the rule groups in `docs/task-briefs.md`; report verified evidence, justified not-applicable criteria, and pending checks. Passing tests or completing one checklist category does not waive other rules. Resolve objective violations or state the limitation before declaring readiness.
- Use tsoa with Express to generate API routes, input validation, and OpenAPI from typed controllers and decorators. Keep controllers small and business rules in services. Do not introduce Zod plus a separate OpenAPI registry for the same contracts. Treat generated routes and specifications as build artifacts; regenerate them automatically in development and build commands, including Docker, and never edit them manually.
- Keep API documentation current and available through Swagger UI at `/api/docs`, with the OpenAPI document at `/api/openapi.json`. Every API change must update its documentation in the same PR. Generate endpoints, authentication/roles, request/response schemas and expected error statuses from typed models and minimal decorators. Keep detailed business/timezone rules and curated examples in docs/api-contracts.md, updated in the same PR; they need not be duplicated in Swagger. Verify API behavior with direct HTTP requests (curl or small scripts) and inspect the served OpenAPI programmatically. Prefer these lower-cost checks over browser automation for backend-only work; opening Swagger UI or using Try it out is not an acceptance requirement. Reserve browser/manual verification for actual interface behavior, visual rendering or accessibility. Generated documentation does not replace business-rule tests or implementation of authorization and error handling.

Planning consolidation does not authorize starting application code; execute after the planning PR is reviewed and merged by the user.
