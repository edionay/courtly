# Project guidance

- Write code, UI text, and repository documentation in English.
- Prefer self-explanatory names and small functions. Add comments only when necessary.
- Keep the implementation small and focused on the challenge's mandatory requirements. Do not add optional bonuses.
- Before making assumptions, consult `docs/challenge.md`, the local structured restatement of the challenge. Follow its mandatory requirements and distinguish them from project decisions. Do not invent requirements.
- Read `docs/decisions.md` for approved decisions and unresolved questions. Proposed decisions are not approved requirements.
- Use PostgreSQL with Prisma. Earlier MongoDB/Mongoose and occupied-slot-array proposals are superseded. Keep snake_case within database artifacts and use camelCase throughout TypeScript and API JSON through Prisma's mapping configuration. Preserve database-level overlap protection in versioned migrations.
- Seed the facility with IANA timezone `America/Sao_Paulo`. Use a generic monetary unit displayed with `$` and two decimal places, without labeling it BRL, USD, or another real currency. Interpret calendar dates and opening hours in the facility timezone and booking instants in UTC.
- Focus on the happy path. Discuss additional edge-case behavior before implementing it.
- Keep unit and integration tests focused, meaningful, and simple to configure. Backend tests must cover concurrency prevention, cancellation timing, and opening hours.
- Never commit directly to `main`. Use a feature branch and a pull request for review and merge.
- Branch names must describe only the feature or work being delivered, in lowercase kebab-case, without AI or agent references or prefixes. Examples: `planning`, `booking-creation`, `court-management`.
- Follow the Google-style commit format without a parenthesized scope: `<type>: <imperative English summary>`. Examples: `feat: add booking creation`, `fix: enforce cancellation window`, `docs: record project decisions`. Use `feat`, `fix`, `docs`, `style`, `refactor`, `perf`, `test`, `build`, `ci`, `chore`, or `revert` as appropriate.
- Commit messages and PR titles and bodies must not include AI attribution, agent signatures, generated-by notices, or agent co-author trailers. This does not remove the challenge's separate requirement to disclose AI usage in the submission decisions.
- The repository currently has no initial commit. Establishing the base branch and first PR remains a planning item; do not silently bypass the PR rule.
- Keep these instructions and the planning documents current as decisions change.
- Use tsoa with Express to generate API routes, input validation, and OpenAPI from typed controllers and decorators. Keep controllers small and business rules in services. Do not introduce Zod plus a separate OpenAPI registry for the same contracts. Treat generated routes and specifications as build artifacts; regenerate them automatically in development and build commands, including Docker, and never edit them manually.
- Keep API documentation current and available through Swagger UI at `/api/docs`, with the OpenAPI document at `/api/openapi.json`. Every API change must update its documentation in the same PR. Document all endpoints, authentication and roles, request and response schemas, examples, expected errors, and applicable business and timezone rules. Verify affected operations through Swagger before considering the delivery complete. Use necessary tsoa metadata annotations sparingly; do not add explanatory comments that repeat the code. Generated documentation does not replace business-rule tests or implementation of authorization and error handling.
- The execution plan must be self-contained: include requirements, approved decisions, API contracts, incremental deliverables, acceptance criteria, dependencies, and enough context for another chat or agent.
- The parent agent is the orchestrator: maintain the plan, prepare self-contained tasks, coordinate implementation and review, and report delivery status. Do not start application implementation until the relevant specification is agreed.
- Delegate implementation to the configured `programador` subagent and review to the configured `revisor` subagent. Both roles are available with `gpt-6-luna` and high reasoning effort. Do not silently substitute another role or model. Each must follow its applicable programming-practices skill.
- For each delivery, give `programador` the specification, approved decisions, file/module ownership, acceptance criteria, verification commands, and relevant dependencies. The developer implements, validates, and opens a feature PR. Then `revisor` reviews the actual PR diff without modifying code. Route actionable findings back to the developer and request another review after fixes. Only the user merges PRs; agents must not merge them. Start dependent deliveries from the merged base.
- The challenge requires the candidate to write the README. Help with discussion and review, but leave README authorship to the candidate.
- Do not submit the challenge as part of implementation or planning.
